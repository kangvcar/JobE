# 技能点切分准则

版本：1.0  
适用范围：职位解析、简历抽取、人岗匹配评测的**唯一**切分依据。  
读者：标注员。读完应能独立完成标注，两人独立标注的技能点集合 Cohen's κ 目标 ≥ 0.70。

术语以仓库根目录 `CONTEXT.md` 为准：**技能点**是最细粒度、可被单独验证的能力单元；**表面形式**是它在原文中出现的字符串原样。本准则只回答一件事：一段文本应被切成几个技能点、每个技能点的边界在哪里。

---

## 1. 总原则（先读完再动手）

1. **可单独验证**：一个技能点对应一项可以独立用「会 / 不会 / 会到什么程度」回答的能力。不能独立验证的，不是技能点。
2. **宁拆不粘**：边界拿不准时，拆成更小的可验证单元，不要把两个能分开考的东西粘成一条。
3. **只标出现的**：原文没写的不补。不要根据岗位常识「脑补」技能点。
4. **表面形式忠实**：`name` 用本准则规定的规范名；`surface_form` 必须是原文子串；`span` 必须满足 `text[start:end] == surface_form`。
5. **位置由字符串匹配回填**：标注员只决定「这是不是技能点、规范名是什么」；起止偏移按首次出现的最长匹配写入。同一技能点在文中多次出现，只标**第一次**出现的区间（评测按集合算，不按次数）。
6. **模板段落里的技能点也要标**：企业套话里若出现可验证技术（如「熟悉 Office」），仍算技能点。是否算「核心必备」由 `necessity` 字段表达，不靠删标来处理。

---

## 2. 切还是不切：决策顺序

对原文中每一处「像能力的短语」，按下列顺序判断。**先命中的规则生效，后面不再看。**

| 顺序 | 问题 | 是 → | 否 → |
| --- | --- | --- | --- |
| Q1 | 这是态度、品德、价值观吗？（责任心、抗压、热爱、积极向上） | **不标** | Q2 |
| Q2 | 这是学历、年限、城市、薪资等**字段**吗？ | 写入字段，**不标为技能点** | Q3 |
| Q3 | 这是可独立验证的能力、工具、语言、框架、协议、方法或可考查的软技能吗？ | 进入第 3 节切分 | **不标** |
| Q4 | 它是否只是修饰语？（「扎实的」「良好的」「较强的」） | 修饰语丢弃，只保留被修饰的技能点 | — |

## 3. 切分规则

### R1 斜杠、顿号、逗号、列举一律拆开

连接符表示列举，不是一个技能点。

| 原文 | 切成 | 不要切成 |
| --- | --- | --- |
| 熟悉 Hadoop/Spark/Flink | Hadoop；Spark；Flink | Hadoop/Spark/Flink |
| 精通 C/C++ | C 语言；C++ | C/C++ |
| 掌握 Python、Java、Go | Python；Java；Go | Python、Java、Go |
| TensorFlow 或 PyTorch | TensorFlow；PyTorch | TensorFlow 或 PyTorch |
| 熟悉 MQTT、CoAP、Modbus 等协议 | MQTT；CoAP；Modbus | 物联网协议（这是上位能力项，不是技能点） |

「等」「为主」「优先」不产生额外技能点。

### R2 工具与方法同时出现：能分开验证就拆

| 原文 | 切成 | 理由 |
| --- | --- | --- |
| 使用 Git 进行版本控制 | Git | 「版本控制」在这里是 Git 的用途，不是独立技能点 |
| 熟悉 Git 与 SVN | Git；SVN | 两个工具 |
| 用 PyTorch 做分布式训练 | PyTorch；分布式训练 | 框架与方法均可独立验证 |
| 基于 Spark 做离线 ETL | Spark；ETL | 工具与方法 |
| 熟悉 Linux 环境下的 Shell 编程 | Linux；Shell | 环境与技能 |

反例：原文只有「分布式训练」，没有出现任何框架名 → 只标「分布式训练」，不要补 PyTorch。

### R3 嵌套技能：有专名就拆出专名，上位词是否保留看它是否可独立验证

「专名」指语言、库、框架、协议、产品、标准的稳定名称。

| 原文 | 切成 | 理由 |
| --- | --- | --- |
| 熟悉 PyTorch 分布式训练 | PyTorch；分布式训练 | 两个可验证单元 |
| 精通 CUDA 编程 | CUDA | 「编程」是使用方式，不单列 |
| 有 Transformer 结构优化经验 | Transformer | 「结构优化」是工作内容，不是技能点 |
| 熟悉 Kubernetes 容器编排 | Kubernetes | 「容器编排」是 K8s 的用途 |
| 熟悉 Docker 与 Kubernetes | Docker；Kubernetes | 两个专名 |
| 熟悉容器技术 | 容器化 | 无专名，保留可验证上位技能点 |
| 熟悉深度学习框架 | 深度学习 | 未点名框架，不虚构 PyTorch |

**禁止**把「熟悉分布式系统设计」切成一个技能点名叫「分布式系统设计」——太宽，无法单独验证。应按原文里真正出现的可验证单元切（如「一致性协议」「RPC」「服务发现」）；若原文只有这一句、没有任何下层专名，则标一个技能点 **分布式系统**（规范名固定为此四字，不要写成「分布式系统设计」）。

### R4 复合修饰不拆成「形容词 + 技能」

| 原文 | 切成 | 不要 |
| --- | --- | --- |
| 高并发系统设计 | 高并发 | 「系统设计」不单列 |
| 低延迟推理 | 模型推理 | 除非原文另有「推理框架」专名 |
| 海量数据存储 | 不标（过宽） | 除非出现 HBase / Redis 等专名 |
| 扎实的数据结构和算法基础 | 数据结构；算法 | 两个可分开考的基础科目 |

### R5 版本、年限、程度不是技能点

| 原文 | 技能点 | 丢弃 |
| --- | --- | --- |
| Python 3.10+ | Python | 3.10+ |
| Spark 3.x | Spark | 3.x |
| 三年以上 Java 经验 | Java | 三年以上（年限写入经验字段） |
| 精通 / 熟悉 / 了解 PyTorch | PyTorch | 程度词。程度写入 `level_hint`（精通=3，熟悉=2，了解=1），不另开技能点 |

同一技能点不要因为程度不同标两次。

### R6 软技能：可考查的标，态度品德不标

**标**（可在面试中出题或用过往交付验证）：

- 沟通能力、跨团队协作、技术写作、英语书面表达、英语口语、项目管理、带人、技术评审

**不标**：

- 有责任心、抗压能力强、热爱学习、积极向上、执行力强、有激情、认同公司文化、吃苦耐劳

| 原文 | 处理 |
| --- | --- |
| 良好的沟通能力与团队合作精神 | 沟通能力；团队合作 |
| 有责任心，能承受加班 | 不标 |
| 英语可作为工作语言 | 英语 |
| CET-6 / 托福 / 雅思 | 英语（证书名写入 surface_form，规范名统一为英语） |

### R7 职责描述 ≠ 技能点

「负责 xxx」是工作内容。只有当职责里嵌了可验证专名或方法时才切出技能点。

| 原文 | 切成 |
| --- | --- |
| 负责推荐系统的迭代优化 | 推荐系统 |
| 负责与产品、运营对接需求 | 不标（职责） |
| 参与机房巡检 | 不标 |
| 负责基于 Flink 的实时数仓建设 | Flink；实时数仓 |

### R8 别名与大小写

规范名见 `eval/lexicon/skills.json` 的 `name`。标注时：

- 英文专名大小写不敏感匹配，规范名用词表写法（`PyTorch` 不是 `pytorch`）。
- 中文别名映射到规范名：`火 Sparks` 不存在；`张量流` → TensorFlow（仅当词表收录该别名）。
- 未入词表但符合 R1–R7 的专名：**仍要标**，`name` 用原文专名的常见写法，并在 `oov` 字段标 `true`。评测技能点级匹配时，OOV 技能点按规范名的小写去空格后精确匹配。

### R9 不要标的东西（硬黑名单）

- 福利：五险一金、带薪年假、下午茶
- 地点、薪资、职级、汇报关系
- 「本科及以上」「计算机相关专业」（学历/专业是字段）
- 「有相关项目经验优先」（空条件，无技能点）
- 「良好的编码习惯」「代码规范」（除非点名 linter / 规范名称如 PEP8 → PEP 8）

## 4. 正例（整句）

**例 A**（人工智能 / 资深）

> 熟悉 PyTorch 或 TensorFlow，有 Transformer、LoRA、分布式训练（DeepSpeed / Megatron）经验，了解 CUDA 与 TensorRT。

切成：PyTorch；TensorFlow；Transformer；LoRA；分布式训练；DeepSpeed；Megatron；CUDA；TensorRT。

**例 B**（大数据 / 初级）

> 掌握 Java/Scala，熟悉 Hadoop、Spark、Hive，有 Kafka 使用经验，了解数据仓库建模。

切成：Java；Scala；Hadoop；Spark；Hive；Kafka；数据仓库。

「建模」在「数据仓库建模」中是方法，规范名用 **数据仓库**；若原文另写「维度建模」则再标 **维度建模**。

**例 C**（智能系统 / 专家）

> 精通 ROS2、SLAM、点云感知，熟悉 Apollo 或 Autoware，有 ISO 26262 功能安全落地经验。

切成：ROS2；SLAM；点云；Apollo；Autoware；ISO 26262。

「功能安全」若单独作为可验证领域知识且无标准号，标 **功能安全**；本句已有 ISO 26262，不重复标。

**例 D**（物联网 / 初级）

> 熟悉 STM32、FreeRTOS，了解 MQTT/CoAP，有 LoRa 或 NB-IoT 项目经验，能看懂原理图。

切成：STM32；FreeRTOS；MQTT；CoAP；LoRa；NB-IoT；原理图。

**例 E**（复合句陷阱）

> 熟悉分布式系统设计，具备高并发、高可用架构经验，熟练使用 Redis、MySQL。

切成：分布式系统；高并发；高可用；Redis；MySQL。

不要只标一个「后端架构」。

## 5. 反例（常见错标）

| 错标 | 为什么错 | 应如何 |
| --- | --- | --- |
| 把「熟悉 Office 软件及 PPT」标成 Office、PPT、软件 | 「软件」不可验证 | Office；PPT |
| 把「PyTorch 分布式训练」标成一条 | 两个可验证单元 | PyTorch；分布式训练 |
| 把「有责任心、沟通能力强」都标上 | 责任心是品德 | 只标沟通能力 |
| 把「计算机网络、操作系统」漏掉 | 基础科目可单独开考 | 计算机网络；操作系统 |
| 把「3 年 Java」标成技能「3年Java」 | 年限不是技能 | Java，年限进字段 |
| 凭岗位常识补上 Linux，但原文没有 | 禁止脑补 | 不标 |
| 同一段里 Python 出现 4 次标 4 条 | 评测按集合 | 只保留首次 span |
| 把「大模型应用」标成 GPT-4 | 未出现专名 | 大模型 |

## 6. 字段与技能点的边界

下列内容**不是技能点**，写入 JD / 简历的字段金标准：

- 岗位标题、公司、城市
- 薪资区间（`salary_min` / `salary_max`，单位：元/月。原文为「K」或「万」时换算后再写数值，span 仍指向原文片段）
- 学历要求（规范值：`博士` / `硕士` / `本科` / `大专` / `不限`）
- 经验要求（规范值：原文年限区间的规范化字符串，如 `3-5年`、`5年以上`、`应届`）

专业要求（「计算机、电子及相关专业」）写入可选字段 `majors`，不计入技能点级评测。

---

## 7. `necessity` 与 `level_hint`

- `required`：出现在「任职要求 / 岗位要求」中，且带「必须 / 精通 / 掌握 / 熟悉」等，或未分区时默认。
- `bonus`：出现在「加分 / 优先 / 了解即可 / plus」。
- `level_hint`：精通/专家=3，掌握/熟悉/良好=2，了解/接触过=1，无法判断则空。

匹配档位计算**只使用技术技能点**（`family != soft`）。软技能仍计入 JD 解析与简历抽取的技能点级 P/R/F1。

---

## 8. 标注单位与一致性

- 一份职位或一份简历由两名标注员**独立**完成，禁止互相看对方结果。
- 分歧提交第三人按本准则仲裁判定，仲裁判定写入金标准。
- 一致性指标：技能点规范名集合的 Cohen's κ（把「该文档是否包含某技能点」视为二元分类，在两人并集词表上计算）。κ < 0.60 的批次整批返工。
- 本项目第一遍因人力限制采用「规则/大模型初标 + 单人按本准则复核」。初标与复核必须分文件存放，报告里不得把复核前的结果当成金标准。

---

## 9. 速查：拿不准时的三问

1. 能不能单独出一道面试题验证它？不能 → 不标或再拆。
2. 原文有没有这个专名或方法名？没有 → 不补。
3. 拆开后每一截是否仍可验证？是 → 拆。
